Root Cause Analysis: POP_JUMP_FORWARD_IF_TRUE Polarity Bug in tick_worker_thread
================================================================================

1. SYMPTOM
----------
The decompilation of strategy.pyc's tick_worker_thread function produces bytecode
that differs from the original: the original uses POP_JUMP_FORWARD_IF_TRUE at
bytecode offset 166 (block 50), but the decompiled source recompiles to
POP_JUMP_FORWARD_IF_FALSE at the same location. This causes 245 true_diffs
across the function.

2. ORIGINAL BYTECODE PATTERN
-----------------------------
The original source code pattern is:

    while True:
        if not self._engine.data_proxy.is_trading_date(datetime.date.today()):
            continue
        now = datetime.datetime.now()
        dt_strf = now.strftime('%H:%M:%S')
        ...

CPython 3.11 compiles this as:

    Block 50:
      LOAD_FAST self._engine.data_proxy.is_trading_date
      LOAD_GLOBAL datetime.date.today
      CALL
      POP_JUMP_FORWARD_IF_TRUE 210    <-- jump to then-body (block 210) on True
      [fall-through to block 168 on False]

    Block 168:  (else/continue path)
      LOAD_GLOBAL time.sleep(60)
      CALL
      POP_TOP
      JUMP_BACKWARD 48                <-- explicit continue to outer loop header

    Block 210:  (then/body path - condition was True, i.e., NOT continue)
      LOAD_GLOBAL datetime.datetime.now()
      ...

The key insight: CPython uses POP_JUMP_FORWARD_IF_TRUE when the source pattern
is `if not cond(): continue`. The TRUE path jumps to the body (skip the continue),
the FALSE path falls through to the continue block.

3. DECOMPILED OUTPUT (INCORRECT)
---------------------------------
The decompiler produces:

    while True:
        if self._engine.data_proxy.is_trading_date(datetime.date.today()):
            now = datetime.datetime.now()
            dt_strf = now.strftime('%H:%M:%S')
            ...
        else:
            continue

This is semantically equivalent to the original, but when recompiled, CPython
generates POP_JUMP_FORWARD_IF_FALSE instead of POP_JUMP_FORWARD_IF_TRUE:

    Block 50:
      ...
      POP_JUMP_FORWARD_IF_FALSE 168   <-- jump to else/continue on False
      [fall-through to block 210 on True]

This produces different bytecode (wrong jump polarity), causing the mismatch.

4. ROOT CAUSE
-------------
The bug occurs in the AST generation path for while-True loop headers that
contain an if-not-continue pattern.

**Primary Location**: `core/cfg/region_ast_generator.py`

**Step-by-step trace**:

a) Block 50 is the header of a while-True inner loop (LoopRegion with
   condition_block=None, is_while_true=True). The inner loop is a child
   of the outer while-True loop (header=48).

b) When the outer loop generates its body, block 50 is encountered as
   the inner LoopRegion's entry and dispatched to _generate_loop(inner_loop).

c) The inner loop's _loop_generate_body processes block 50 as the header
   block via _loop_handle_header (line 6805).

d) In _loop_handle_header, the code checks multiple conditions:
   - condition_block == header? No (condition_block is None)
   - _header_if_region? No (region_analyzer's _should_skip_block_for_if_region
     returned True, preventing IfRegion creation for block 50)
   - condition_block is not None? No (it's None)
   - PLACEHOLDER_OPS check for _loop_handle_header_no_condition? No
     (block 50 starts with LOAD_FAST, not NOP/RESUME/CACHE)
   - _header_if_region (2nd check)? Still None

e) Since none of the special conditions match, block 50 falls through to
   _generate_block_statements (line 8744 in _loop_handle_header_no_condition's
   fallback, or the generic block processing in the loop body generator).

f) _generate_block_statements processes block 50's instructions generically.
   It sees a POP_JUMP_FORWARD_IF_TRUE instruction but does NOT account for
   the polarity difference. It generates:

     {'type': 'If', 'test': <is_trading_date(...)>,
      'body': [<time.sleep(60)>, <Continue>], 'orelse': []}

   The test expression is is_trading_date(...) WITHOUT the 'not' negation,
   and the body contains the continue path. When rendered, this becomes
   `if is_trading_date(...): ... else: continue` which produces IF_FALSE
   instead of the original IF_TRUE.

**Contrast with _loop_extract_self_loop_stmts**:
When called, _loop_extract_self_loop_stmts (line 7576) DOES correctly
generate the AST with 'not':

    {'type': 'If', 'test': {'type': 'UnaryOp', 'op': 'not',
                            'operand': <is_trading_date(...)>},
     'body': [<time.sleep(60)>, <Continue>], 'orelse': []}

This would render as `if not is_trading_date(...): continue`, which
recompiles to the correct POP_JUMP_FORWARD_IF_TRUE.

However, _loop_extract_self_loop_stmts is never called for block 50
because the code path bypasses it.

**Secondary Location**: `core/cfg/region_analyzer.py:14635-14658`

The _should_skip_block_for_if_region function skips block 50 for IfRegion
creation. When a while-True loop header (condition_block=None) has two
conditional successors, it checks for two patterns:
  - is_if_break_pattern: then_succ ends with RETURN_VALUE
  - is_if_break_else_continue: else_succ ends with JUMP_BACKWARD

For block 50:
  - then_succ = 168 (sorted by offset) — CONTINUE, ends with JUMP_BACKWARD
  - else_succ = 210 — LOOP_BODY, ends with POP_JUMP_FORWARD_IF_FALSE

Neither pattern matches because:
  - is_if_break_pattern requires then_last to be RETURN_VALUE (it's JUMP_BACKWARD)
  - is_if_break_else_continue requires else_last to be JUMP_BACKWARD (it's
    POP_JUMP_FORWARD_IF_FALSE)

The function then returns True (skip), preventing IfRegion creation.

The fundamental issue: the pattern recognition sorts successors by offset
(168 < 210), making 168 the "then" and 210 the "else". But with
POP_JUMP_FORWARD_IF_TRUE, the jump target (210) is the TRUE/then path,
and the fall-through (168) is the FALSE/else/continue path. The code
doesn't consider the jump polarity when assigning then/else roles.

5. FIX STRATEGY
---------------
Two complementary fixes are needed:

**Fix A**: In _should_skip_block_for_if_region (region_analyzer.py:14635-14658),
add recognition of the "if-not-continue" pattern for while-True loop headers
with POP_JUMP_FORWARD_IF_TRUE. When the jump instruction is IF_TRUE and the
jump target is a LOOP_BODY block while the fall-through is a CONTINUE block,
this is a valid if-not-continue pattern that should NOT be skipped for
IfRegion creation. Alternatively, create the IfRegion with proper
then/else assignment based on jump polarity.

**Fix B**: In _loop_handle_header (region_ast_generator.py), when processing
a while-True loop header whose last instruction is POP_JUMP_FORWARD_IF_TRUE
and one successor is a CONTINUE block (fall-through) while the other is a
LOOP_BODY block (jump target), generate the AST with the 'not' negation:

    if not <condition>:
        continue

This is equivalent to the current `if <condition>: ... else: continue` but
preserves the correct jump polarity on recompilation.

The preferred fix is **Fix B** because:
1. It's more localized — only affects header processing, not region analysis
2. The region analyzer's skip logic serves a valid purpose (preventing
   spurious IfRegions in back-edge recheck patterns), and modifying it
   risks regressions
3. The _loop_extract_self_loop_stmts already handles this correctly but
   isn't reached; routing to it or duplicating its logic is simpler

6. REPRODUCTION SCRIPTS
------------------------
All scripts in test_repro/r02/ that use the pattern `if not cond(): continue`
inside a while-True loop produce POP_JUMP_FORWARD_IF_TRUE in the original
bytecode but get decompiled as `if cond(): ... else: continue` which produces
POP_JUMP_FORWARD_IF_FALSE on recompilation.

Key repro scripts:
  - repro_01_if_not_continue.py: simplest case
  - repro_04_if_not_var_continue.py: simple truthy variable
  - repro_06_if_not_continue_multi_stmt.py: with additional body statements
  - repro_10_multiple_if_not_continue.py: multiple if-not-continue guards

7. VERIFICATION
---------------
After the fix, decompiling the reproduction scripts should produce:

    while True:
        if not cond():
            continue
        ...

which recompiles to POP_JUMP_FORWARD_IF_TRUE, matching the original bytecode.

For the tick_worker_thread case, the fix should produce:

    while True:
        if not self._engine.data_proxy.is_trading_date(datetime.date.today()):
            continue
        now = datetime.datetime.now()
        dt_strf = now.strftime('%H:%M:%S')
        ...

which is the exact original source pattern.
