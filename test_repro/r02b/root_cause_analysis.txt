================================================================================
ROOT CAUSE ANALYSIS: tick_worker_thread Inner Elif Chain Flattening Bug
================================================================================
Date: 2026-09-14
File: strategy.pyc (IQEngine/plugins/plugin_fly_data/strategy/)
Function: tick_worker_thread
Bug Index: r02b

================================================================================
1. SUMMARY
================================================================================

The decompiler incorrectly flattens a nested if/elif chain inside an outer
elif branch when the outer elif's "else" body (the FALSE-path continuation)
shares the same code block as the inner if's TRUE body. This shared-block
optimization by CPython causes the decompiler to lose the nesting boundary
between the inner elif chain and the outer elif chain, merging them into
a single flat chain with "pass" bodies and corrupted control flow.

================================================================================
2. ORIGINAL SOURCE STRUCTURE (reconstructed from bytecode)
================================================================================

The tick_worker_thread function has this structure inside a while-True/try:

    if AccountType.FUTURE.value in accounts:
        if is_future_tradetime_now(dt_strf):
            queue.put((now, EventEnum.HANDLE_TICK))
            time.sleep(3)
        elif not (dt_strf > '15:15:00' or dt_strf < '08:30:00'):
            if '11:30:00' < dt_strf < '12:30:00':
                time.sleep(60)                # <-- BLOCK A (offset 568)
            elif '08:30:00' <= dt_strf < '08:59:00' or ...:
                time.sleep(60)                # <-- BLOCK B (offset 674)
            elif '08:59:00' <= dt_strf < '09:00:00' or ...:
                time.sleep(0.5)               # <-- BLOCK C (offset 780)
        else:                                 # dt_strf > 15:15 or < 08:30
            time.sleep(60)                    # <-- BLOCK A again! (offset 568)
    elif is_stock_tradetime_now(dt_strf):     # <-- OUTER elif (offset 822)
        queue.put((now, EventEnum.HANDLE_TICK))
        time.sleep(3)
    elif not (dt_strf > '15:00:00' or dt_strf < '09:00:00'):
        ... (similar nested if/elif chain)

================================================================================
3. CPython SHARED-BLOCK OPTIMIZATION
================================================================================

CPython 3.11 optimizes the above code by merging BLOCK A (the inner if's
TRUE body) with the elif's else body into a single shared code block at
offset 568. The bytecode control flow is:

    Offset 512-534: elif not(dt_strf > '15:15' or dt_strf < '08:30')
      POP_JUMP_IF_TRUE -> 568    (TRUE path: dt_strf > 15:15 or < 08:30)
      fall-through -> 536        (FALSE path: 08:30 <= dt_strf <= 15:15)

    Offset 536-566: if '11:30' < dt_strf < '12:30'
      JUMP_FORWARD -> 568        (TRUE path: shared block A)
      JUMP_FORWARD -> 612        (FALSE path: next inner elif)

    Offset 568-610: time.sleep(60) + continue  <-- SHARED BLOCK
      (reached from BOTH the elif TRUE path AND the inner if TRUE path)

This optimization is valid because both paths execute identical code.
However, it creates a CFG where block 568 has predecessors from TWO
different conditional contexts:
  1. The "elif not(...)" condition (via POP_JUMP_IF_TRUE at 522/534)
  2. The inner "if '11:30' < dt_strf < '12:30'" condition (via JUMP at 562)

================================================================================
4. DECOMPILER BUG: _check_elif_chain Chain Boundary Loss
================================================================================

The decompiler's `_check_elif_chain` function (region_analyzer.py:17250)
processes the elif chain recursively. When it encounters the "elif not(...)"
condition, it:

1. Identifies the TRUE successor (offset 568 = time.sleep(60)) as the
   elif's then-body or else-body
2. Identifies the FALSE successor (offset 536 = inner if condition) as
   a potential nested elif
3. Recursively calls _check_elif_chain on the inner if/elif chain

The bug occurs in step 1-2 interaction. The _check_elif_chain function
uses `_collect_branch_blocks` to gather the "then" and "else" blocks of
each elif condition. When it collects the "then" blocks for the inner
if condition (offset 536), it includes block 568 as the inner if's body.

But block 568 is ALSO reachable from the outer elif's TRUE path. The
decompiler does not recognize that block 568 serves as the body for
TWO different conditions. Instead, it:

a) Assigns block 568 to ONE context (typically the elif's else-body or
   the first elif body it encounters)
b) Leaves the OTHER context with no body, generating "pass"
c) This breaks the inner elif chain boundary

CRITICAL CODE PATH in _check_elif_chain (region_analyzer.py:17656-17700):

    inner_cond_succs = list(inner_condition_block.conditional_successors)
    inner_then_succ, inner_else_succ = sorted(inner_cond_succs, ...)
    inner_merge = self._find_nearest_common_post_dominator(inner_then_succ, inner_else_succ)

The issue: inner_then_succ (offset 568) is a shared block. The NCPD
computation finds that inner_then_succ and inner_else_succ both eventually
reach offset 1286 (the loop continue point). But the decompiler doesn't
account for the fact that inner_then_succ (568) is also the target of
the OUTER elif's TRUE path.

When _collect_branch_blocks collects the inner elif's "else" blocks
(starting from inner_else_succ = offset 612), it traverses through
the inner elif chain (612-718) and then continues to offset 822 (the
outer elif "is_stock_tradetime_now") because there's no merge boundary
to stop it. The inner elif chain's FALSE path naturally falls through
to the outer elif conditions.

This causes:
- Offset 822 (outer elif) gets absorbed into the INNER elif chain
- Offset 982+ (second outer elif chain) also gets absorbed
- The outer elif conditions appear as inner elif conditions
- The outer elif bodies become "pass" (their code was already attributed
  to the wrong nesting level)

5. SPECIFIC MANIFESTATIONS IN THE DECOMPILED OUTPUT
================================================================================

a) "if '11:30:00' < dt_strf < '12:30:00': pass"
   - The inner if body should be time.sleep(60), but the shared block
     is attributed to the outer elif's else, leaving the inner if with
     no body (pass)

b) "elif '08:30:00' <= dt_strf < '08:59:00' or Exception:"
   - The "or Exception" is a corruption from the decompiler mis-parsing
     the or-chain when the elif boundary is lost. The POP_JUMP_IF_FALSE
     for the second or-clause at offset 718-778, when its FALSE path
     (offset 1286 = loop continue) is misidentified as the inner if's
     merge point, the remaining bytecode (which is actually the outer
     elif) gets misinterpreted as part of the or-chain condition.

c) "elif is_stock_tradetime_now(dt_strf):" inside the FUTURE branch
   - This is the OUTER elif (offset 822) being absorbed into the inner
     chain. It should be at the same level as "if FUTURE.value in accounts"

d) Outer elif bodies become "pass"
   - "elif is_stock_tradetime_now(dt_strf): pass" - the actual body
     (queue.put + sleep(3) at offset 864-980) was already placed inside
     the mis-nested inner chain

================================================================================
6. ROOT CAUSE: SHARED-BLOCK ELIF/ELSE MERGE AMBIGUITY
================================================================================

The fundamental issue is that the decompiler assumes each code block
belongs to exactly one conditional branch (region_analyzer.py Principle 2:
"每块唯一归属"). This assumption breaks when CPython's optimizer merges
identical branch bodies into shared blocks.

In the specific pattern:

    elif not(A or B):       <- TRUE-skip -> shared_body
        if C:               <- TRUE -> shared_body
            shared_body     <- SAME BLOCK serves TWO conditions
        elif D:
            different_body

The decompiler cannot determine whether shared_body is:
1. The else-body of "elif not(A or B)" (when A or B is true)
2. The then-body of "if C" (when C is true)
3. BOTH (the correct answer)

Because it assigns shared_body to only one context, the other context
gets "pass", and the control flow structure is corrupted.

     for the shared-block pattern, leading to incorrect inner_merge

================================================================================
8. FIX APPROACH
================================================================================

The fix requires detecting the shared-block pattern in _check_elif_chain:

When the elif condition's TRUE-successor (the "skip" target for
POP_JUMP_IF_TRUE in an "elif not(A or B)" pattern) is the SAME block
as the inner if condition's TRUE-successor, this indicates a shared
block optimization. The decompiler should:

1. Detect that the elif's TRUE-successor block has predecessors from
   BOTH the elif condition AND the inner if condition
2. Recognize this as a shared-body pattern where the block serves as
   both the elif's else-body and the inner if's then-body
3. DUPLICATE the shared block semantically (generate the same code for
   both the inner if body and the elif else body)
4. Set the inner elif chain boundary correctly so the outer elif
   conditions are NOT absorbed into the inner chain

Specific check to add in _check_elif_chain after computing
inner_then_succ and inner_else_succ:

    # Detect shared-block pattern: elif's skip-target == inner if's then-body
    if (inner_then_succ is not None
        and inner_then_succ in elif_skip_targets  # blocks targeted by elif's POP_JUMP_IF_TRUE
        and len(inner_then_succ.predecessors) >= 2):
        # Shared block: duplicate for inner if body, set correct chain boundary
        # inner_merge should be set to the next outer elif condition block
        # (offset 822 in the tick_worker_thread case)

Alternatively, the W14-C fix (currently disabled at line 24230) could
be re-enabled and enhanced to handle this specific pattern. The shared
block should be pruned from one branch's collected blocks and assigned
to the other, with the pruned branch getting a duplicate.

================================================================================
10. IMPACT ASSESSMENT
================================================================================

This bug affects any Python code with the pattern:
- while True / try / except wrapper
- if/elif chain where an elif has "not(A or B)" condition
- Inside the elif body, a nested if/elif chain
- The elif's else-body (when A or B is true) is identical to the
  inner if's then-body

This pattern is common in time-based trading/market systems where:
- Different time ranges trigger the same action (sleep)
- The "not in trading time" else case does the same thing as
  the "lunch break" inner if case

The bug produces functionally incorrect decompiled code that will
behave differently from the original when recompiled, because:
- pass does nothing while time.sleep(60) delays execution
- The outer elif conditions are never reached from their proper context
- The control flow timing is completely wrong
