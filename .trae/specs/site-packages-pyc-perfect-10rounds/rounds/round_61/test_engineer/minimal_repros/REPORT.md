# Test Engineer Report: Decompilation Failures in fly/common/flytools.pyc

## Summary
The pyc file has 2 functions with bytecode mismatches out of 65 total:
1. `<module>`: orig=388 instructions, decomp=392, first diff at index 344
2. `modify_batcktes_info`: orig=217 instructions, decomp=222, first diff at index 8

## Root Cause Analysis

### Failure 1: f-string `f'{user_id!s}.{filename!s}.lock'` reconstructed as `'user_id.filename.lock'`

**Root Cause:** The `_build_class_def` fallback decorator scanner (region_ast_generator.py:2617-2644) and the `_reconstruct_decorator_chain` (region_ast_generator.py:2079-2278) both scan backward from `LOAD_BUILD_CLASS`/`MAKE_FUNCTION` and collect `LOAD_NAME`/`LOAD_GLOBAL`/`LOAD_DEREF` instructions as decorator entries. However, **the class decorator fallback scanner at line 2617 does NOT merge adjacent `LOAD_ATTR` chains** into Attribute nodes like the function decorator scanner does (lines 2178-2214). More critically for the f-string issue:

The f-string reconstruction fails in the **non-ternary path** — when the f-string appears as a simple expression (not inside a ternary). The `ExpressionReconstructor.reconstruct()` method in `ast_generator_v2.py` correctly processes `FORMAT_VALUE` (lines 1813-1863) and `BUILD_STRING` (lines 1865-1889) to produce `JoinedStr`/`FormattedValue` nodes. However, the problem occurs at the **region level** in `region_ast_generator.py`.

When the f-string bytecode sequence `LOAD_FAST user_id → FORMAT_VALUE 1 → LOAD_CONST '.' → LOAD_FAST filename → FORMAT_VALUE 1 → LOAD_CONST '.lock' → BUILD_STRING 4` is processed by `_generate_block_statements` → `_build_statements_from_instructions`, the instructions are accumulated into `stmt_instrs` and then passed to `_build_store_statement`. The `_build_store_statement` method delegates to `expr_reconstructor.reconstruct()`.

The key problem is in `ast_generator_v2.py:1866-1889` (BUILD_STRING handler): when building a `JoinedStr` from the stack, the code pops `count` values but **skips PUSH_NULL markers** (line 1877). If a `PUSH_NULL` marker somehow gets mixed into the stack (from a prior `LOAD_GLOBAL NULL+...` instruction that emits both a Name and a PUSH_NULL), the count is off, causing the stack to be misaligned. This leads to BUILD_STRING receiving wrong values and potentially collapsing the entire f-string into a single Constant string.

**Responsible methods:**
- `ast_generator_v2.py:1866-1889` — BUILD_STRING handler in ExpressionReconstructor
- `ast_generator_v2.py:387-393` — LOAD_GLOBAL/LOAD_FAST handler (does not preserve LOAD instruction type)
- `region_ast_generator.py:15549-15581` — FORMAT_VALUE handler in the ternary context

**The deeper issue:** When `LOAD_GLOBAL` with arg having bit 0 set (NULL + name form) is processed by `ast_generator_v2.py:387`, it emits `{'type': 'Name', 'id': argval, 'ctx': 'Load'}` — a plain Name node. The `PUSH_NULL` that CPython emits before `LOAD_GLOBAL NULL+name` is tracked separately as `{'type': 'PUSH_NULL'}`. But in `BUILD_STRING` at line 1874, `count=4` means pop exactly 4 non-PUSH_NULL values. If the f-string stack is correct (4 values: FormattedValue, Constant, FormattedValue, Constant), BUILD_STRING should produce JoinedStr with 4 parts. The failure mode is when the f-string bytecode gets split across multiple blocks or when the expression reconstructor processes an incomplete instruction sequence (e.g., missing the FORMAT_VALUE instructions), causing the stack to contain only a single Constant string `'user_id.filename.lock'` instead of the 4-part JoinedStr.

### Failure 2: `@unique` decorator emits LOAD_NAME instead of PUSH_NULL+LOAD_GLOBAL

**Root Cause:** The `_build_class_def` method in `region_ast_generator.py:2617-2644` has a **fallback decorator scanner** that walks backward from `LOAD_BUILD_CLASS` to find decorator names. This scanner at line 2625 collects `LOAD_NAME`, `LOAD_GLOBAL`, `LOAD_DEREF`, and `LOAD_ATTR` instructions and creates simple `{'type': 'Name', 'id': argval, 'ctx': 'Load'}` decorator nodes (line 2627).

When the code generator (`code_generator.py:2582-2591`, `_generate_class_def_dict`) encounters a `Name` decorator, it emits `@unique` which compiles to `LOAD_NAME unique`. But the **original** bytecode uses `LOAD_NAME unique` + `PUSH_NULL` + `LOAD_BUILD_CLASS` pattern, where the `LOAD_NAME` for `@unique` is actually a **global** reference that CPython compiles as `LOAD_NAME` at module level.

The actual mismatch is at index 344 where the original has `PUSH_NULL` but the decompiled has `LOAD_NAME 'unique'`. This means the decorator is being emitted in the **wrong position** or with the **wrong instruction sequence**. The `@unique` decorator should produce `LOAD_NAME unique` → `PUSH_NULL` → `LOAD_BUILD_CLASS` → `LOAD_CONST <code>` → `MAKE_FUNCTION` → `LOAD_CONST 'FileLockException'` → `LOAD_NAME Enum` → `PRECALL 3` → `CALL 3` → `PRECALL 0` → `CALL 0` → `STORE_NAME FileLockException`. 

The decompiler is emitting the decorator via `LOAD_NAME 'unique'` at a position where the original has `PUSH_NULL`. This means the decorator's `LOAD_NAME` instruction is being placed one position too late, shifting all subsequent instructions. The root cause is that the code generator emits the decorator as a separate `@unique` line which generates `LOAD_NAME unique` before the class definition, but the PUSH_NULL that should precede LOAD_BUILD_CLASS is being lost or the LOAD_NAME for `unique` is being emitted at the position of PUSH_NULL.

**Responsible methods:**
- `region_ast_generator.py:2617-2644` — fallback decorator scanner for classes
- `region_ast_generator.py:2608` — `_extract_decorators` for class decorator extraction
- `code_generator.py:2582-2591` — `_generate_class_def_dict` decorator emission
- `code_generator.py:2370-2431` — `_generate_decorator` method

### Failure 3: `fp` emitted as LOAD_GLOBAL instead of LOAD_FAST

**Root Cause:** The `fp` variable in `with open(...) as fp:` is a **local variable** that CPython emits as `STORE_FAST fp` / `LOAD_FAST fp`. However, the decompiler is producing `LOAD_GLOBAL fp` for it.

The issue is in how the `with` statement's `as` variable is represented in the AST. When `_generate_with` creates the `With` AST node at `region_ast_generator.py:25070-25076`, the `optional_vars` is set to `{'type': 'Name', 'id': target, 'ctx': 'Store'}`. This Name node has `ctx: 'Store'` but **does not preserve whether the original bytecode used STORE_FAST, STORE_NAME, or STORE_GLOBAL**. 

When the code generator compiles `with open(path, 'r') as fp:`, it generates `LOAD_GLOBAL open` → `LOAD_FAST path` → `LOAD_CONST 'r'` → `CALL` → `BEFORE_WITH` → `STORE_FAST fp`. The `STORE_FAST fp` is the with-item's `as` binding. However, when recompiling the decompiled source, the compiler sees `fp` as a local variable (correctly) and generates `STORE_FAST fp` + `LOAD_FAST fp`. 

The mismatch `LOAD_GLOBAL fp` vs `LOAD_FAST fp` occurs when the decompiler **incorrectly classifies `fp` as a global** rather than a local. This happens in the expression reconstructor at `ast_generator_v2.py:387-393` where ALL LOAD instructions (`LOAD_NAME`, `LOAD_GLOBAL`, `LOAD_FAST`, `LOAD_DEREF`) are converted to the same `{'type': 'Name', 'id': argval, 'ctx': 'Load'}` node — the original instruction type is **lost**. When the code generator later encounters a `Name` node, it must decide whether to emit `LOAD_FAST`, `LOAD_GLOBAL`, or `LOAD_NAME`. The code generator (`code_generator.py`) compiles source code strings, so it relies on CPython's compiler to make this distinction. But if the with-statement structure is incorrect (duplicate variable assignments, misnested blocks), the compiler may not see `fp` as assigned in the with clause and treat it as a global.

The actual root cause for the `LOAD_GLOBAL fp` is likely that the decompiler is generating code where `fp` appears **outside** the with block's scope (e.g., the nested with statements are flattened, causing `fp` to be used after its scope ends), making the CPython compiler treat it as a global/free variable.

**Responsible methods:**
- `region_ast_generator.py:23816-25094` — `_generate_with` method (with statement generation)
- `region_ast_generator.py:25070-25076` — `optional_vars` creation for with-items
- `ast_generator_v2.py:387-393` — LOAD instruction → Name node (loses instruction type info)
- `region_ast_generator.py:24310-24322` — with body block filtering of target STORE

## Expected Fix Descriptions

### Fix 1: f-string reconstruction
- **Location:** `ast_generator_v2.py:1866-1889` (BUILD_STRING handler) and the block-level statement builders
- **Fix:** Ensure that when `_build_statements_from_instructions` or `_generate_block_statements_body` processes a block containing `FORMAT_VALUE` + `BUILD_STRING` sequences, the **complete instruction sequence** from the first LOAD to the final BUILD_STRING is passed to `expr_reconstructor.reconstruct()` as a single unit, not split across statement boundaries. The current code may be splitting the f-string instructions into separate statement groups, causing the FORMAT_VALUE instructions to be processed in one group and the BUILD_STRING in another (or vice versa), resulting in a partially-constructed JoinedStr that collapses to a Constant string.
- **Also fix:** The `comprehension_generator.py:1031` returns `delta=0` for FORMAT_VALUE, but FORMAT_VALUE with flags<2 has net stack effect of 0 (pops 1, pushes 1), while FORMAT_VALUE with flags>=2 (has format_spec) pops 2 and pushes 1, delta=-1. This incorrect delta can cause stack misalignment when FORMAT_VALUE appears in comprehension contexts.

### Fix 2: @unique decorator on class
- **Location:** `region_ast_generator.py:2617-2644` (fallback class decorator scanner)
- **Fix:** The fallback scanner at line 2617 creates Name nodes without preserving the original instruction type. When the code generator re-emits these, it may use LOAD_NAME (module level) or LOAD_GLOBAL depending on context. The fix should either:
  1. Merge this fallback scanner with `_reconstruct_decorator_chain` (line 2079) which has more robust handling, or
  2. Track the original `opname` (LOAD_NAME vs LOAD_GLOBAL) in the decorator Name node so the code generator can emit the correct instruction, or
  3. Ensure the PUSH_NULL instruction that precedes LOAD_BUILD_CLASS in the original bytecode is correctly accounted for when counting decorator-related CALL sequences.
- The key issue is that at module level, CPython uses `LOAD_NAME` for `unique`, which has different stack behavior than `LOAD_GLOBAL` (LOAD_NAME also checks locals and globals). The decorator scanner needs to preserve this distinction.

### Fix 3: with-statement `as` variable scoping (LOAD_GLOBAL vs LOAD_FAST)
- **Location:** `region_ast_generator.py:25070-25076` (with item optional_vars) and `region_ast_generator.py:24310-24322` (with body STORE filtering)
- **Fix:** The with-statement body generation needs to ensure that:
  1. The `as` variable's STORE instruction is **only** emitted via the withitem's `optional_vars`, never as a standalone Assign in the body (currently done at line 24318-24322 by filtering `region.target` from body stmts).
  2. For **nested with statements** (like `with open(...) as fp:` inside another with), the body block assignment filtering must correctly identify which STORE belongs to which with-item. The current code only checks `region.target` (line 24312), which may miss nested targets.
  3. The AST Name nodes need to preserve whether the original bytecode used STORE_FAST/LOAD_FAST vs STORE_NAME/LOAD_NAME vs STORE_GLOBAL/LOAD_GLOBAL, so the code generator can emit the correct instruction type. Currently `ast_generator_v2.py:387-393` flattens all LOAD variants to `Name(id, ctx='Load')`, losing this information.
