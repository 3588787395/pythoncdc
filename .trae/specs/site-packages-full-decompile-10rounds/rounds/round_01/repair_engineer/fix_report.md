## 根因分析

### 区域分析器结构识别错误
原始 Python 源码结构（推断）:
```python
def get_python_version():
    import traceback
    import sys
    flag = '0'
    try:
        # if-elif-else 判断 Python 版本
    except:
        traceback.print_exc()
    try:
        globals()['python_version'] = flag
    except:
        pass
    return flag
```

反编译器生成的结构:
```python
    try:
        # if-elif-else
    except:
        traceback.print_exc()
    else:
        return flag           # ← 应在 try-except 之外
    finally:
        globals()['python_version'] = flag  # ← 应是第二个 try-except 的 except handler
```

### 技术根因
1. **Step 5 扩展**: `_parse_exception_table` 的 Step 5 迭代扩展将 except handler 496 的 try 范围从 `[404,406)` 扩展到 `[24,460)`，使其包含 except handler 406 的范围 `[24,404)`
2. **分类错误**: 496 块 (PUSH_EXC_INFO + ... + RERAISE，无 POP_EXCEPT) 被分类为 `finally`，实际是 `bare except` handler
3. **配对逻辑**: 496 (finally) 与 406 (except) 配对成功，形成 try-except-else-finally 结构

### 核心困难
try-except-finally 和 try-except;try-except 的异常表条目模式在所有测试的判据下无法区分:
- 两种结构的 finally/except2 原始条目 try 范围都不覆盖 except1 handler 入口
- 两种结构的 finally/except2 原始条目 try 范围都不与 except1 的 try 范围重叠
- 两种结构的 finally/except2 和 except1 的原始 try_start 都不相同

### 修复方向建议（供后续轮次参考）
1. **在代码生成阶段修复**: 不修改区域分析器，在 `_generate_try` 中将 finally_blocks 中实际是 bare except handler 的块移到 except_handlers
2. **基于 CFG 后继分析**: 检查 finally handler 块的后继链是否到达一个独立的 return 块（不经过 except handler），以区分 finally 和 bare except
3. **基于异常表 depth 分析**: 分析 depth=0 和 depth=1 条目的组合模式
