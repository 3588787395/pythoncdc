## 1. 根因证据（偏移级）

### 1.1 W11-A：finally 体语句重排/拆分（主缺陷）

原 finally 体顺序（正常路径副本 offset 4038–4838）：

| 序 | 语句 | 原偏移 |
|---|---|---|
| 1 | `if run_type == BACKTEST and plugin_system_log.enabled is False:` → `with open(...) as fa: fa.write(...)` | 4038–4380 |
| 2 | `engine.event_bus.publish_event(Event(EventEnum.SYSTEM_EXIT, code=code, exception=ex))` | 4382–4484 |
| 3 | `engine.calendar_dt = None` | 4486–4498 |
| 4 | `if TRADING:` → `if load_plugin_flag is False:` → import/print/call | 4500–4734 |
| 5 | `plugins_manager.release(code, ex)` | 4736–4778 |
| 6 | `print(_('插件卸载完成，引擎退出'))` | 4780–4834 |

反编译产物发射为 `[1 的 if 被抽空成 pass] → [5] → [6] → [4] → [1 的裸 with] → 泄漏到 finally 外的 [2][3][4] → 尾部空体 with 副本 → RETURN_VALUE 结尾`。

四个指纹：
- **错序**：复合块（IfRegion⊂WithRegion）与其后的兄弟线性段次序颠倒；
- **拆散**：with 头部（open…BEFORE_WITH…STORE_FAST fa）与体（fa.write…POP_TOP）分离到不同位置；
- **空体副本**：同一 with 在尾部以空体重复发射一次；
- **终止符漂移**：异常路径副本结尾的 `RERAISE/COPY/POP_EXCEPT/RERAISE`（5640–5646）被替换为 `LOAD_CONST None; RETURN_VALUE`（5874–5884），连带 co_exceptiontable 膨胀。

与已修家族的区别：R07 docstring/嵌套 if 折叠、R08 handler 误吸收、R09 循环吞并兄弟块、R10 WithRegion 吞并紧前兄弟表达式语句（均为"少发射"）；W11-A 是"多发射+错序+重复副本"，勿套用旧修法。

### 1.2 W11-B：孤立 NOP 构造丢失

offset 3636 孤立 NOP（位于 `STORE_FAST executor`@3634 与 `executor.run(bar_dict)`@3638 之间）：无任何跳转指向它、异常表区间 `3498–3732→3764` 连续覆盖（排除嵌套 try/finally）。实验矩阵（r11_probe7.py）证实此类 NOP 来自编译器折叠残留（如两语句间的 `while False: pass`）。反编译输出完全丢弃该位置，re-compile 后从 3636 起全部指令 −2 错位。

## 2. 嫌疑方法线索（按优先级）

1. **W11-A 首要嫌疑**：`core/cfg/exception_handler.py`
   - `_collect_finally_body`（≈L1294）：检查其收集 finally 体块的排序依据——是否按"块遍历可达序"而非"原偏移序"排列；复合块 IfRegion+WithRegion 是否被从线性序列中摘除后延迟追加。
   - `_is_real_finally_block`（≈L1372）与 `is_finally_normal_path_block`（≈L1110）：确认正常路径副本与异常路径副本（PUSH_EXC_INFO 后的第二份）的终止块识别；异常副本应以 RERAISE 序列收尾而非被改写为 RETURN_VALUE。
2. **W11-A 次要素疑**：`core/cfg/region_analyzer.py`
   - `_coalesce_split_try_except_finally_regions`（≈L7120）与 `_enhance_finally_copy_annotation`（≈L21587）：验证 finally 两份副本的块归属合并时是否打乱偏移序；`_identify_empty_body_finally_regions`（≈L7141）可能与空体 with 副本的产生相关。
   - 发射端：`core/cfg/ast_generator_v2.py` ≈L17685 起（`_has_return_in_finally_path` 一带）检查 finally 体语句的拼接顺序逻辑。
   - 定位手段：对 repro_01 打印 FinallyRegion 内子 region 列表及各自首条指令 offset，直接观察错序发生点。
3. **W11-B**：`core/cfg/structured_analyzer.py` NOP 处理机制（≈L176 关键修复注释、≈L3174 `_identify` 系列、≈L2413/L2714/L3305 多处"只含 NOP 块"判定）
   - 现状：孤立 NOP 块被识别为虚拟 if 结构后在代码生成阶段归零发射。建议：当 NOP 满足"语句边界 + 无任何跳转指向 + 非 try 体首标记（try 标记由 TryRegion 自己持有）"时，在对应源码位置发射等价构造 `while False:` + 缩进 `pass`（实测恰好编译为单个孤立 NOP、无附加跳转；已在 r11_correct_src_else.py 全量验证）。注意与现有 `if True:` 虚拟结构判定互斥，避免双重归类。
4. 回归自检清单：禁止改动 R07–R10 已修逻辑（docstring 折叠、boolop 豁免、handler 可达性 BFS、loop 兄弟块判定、with pre-BEFORE_WITH 终止符集）；else 子句生成与 restore 位置的现有行为必须保持。
