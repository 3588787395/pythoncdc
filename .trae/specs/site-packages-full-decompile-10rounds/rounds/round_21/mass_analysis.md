### SWAP-return 家族块级实证（Wave2 深挖）

to_pd_result(common_func.pyc @386-406) 原始形态：

```
[内层 CALL][KW_NAMES][PRECALL/CALL 外层]   # f(g(x, **kw))
[SWAP 2]                                   # 弃栈顶隐藏项、保结果
[POP_TOP]
[RETURN_VALUE]
[JUMP_FORWARD → merge]                     # 另一臂汇入
```

- `_generate_return_ast` 已具备 has_swap_pattern 处理（L40107-40124），
  说明 Return 构建器无缺；缺陷在该块未以「终态返回块」身份进入该路径，
  而被顺序路径渲染为 Expr 语句（call+POP_TOP）+ 追加隐式 return None，
  并把后继 JF 臂替换为显式 return None。
- 下一步（R22 首任务）：对该签名块（末三条=SWAP,POP_TOP,RETURN_VALUE）
  在 _process_if_blocks/GBS 分发处加角色判定，直接走 _generate_return_ast；
  同族样本：np_tp_pd、ModelGraph._get_influence_task、get_server_ip_info、
  api_get_from_zeromq（EXC 变体含 PUSH_EXC_INFO/RERAISE）。

#### 已否决方案（勿重复）
GBS 入口按「末三条 SWAP,POP_TOP,RET」签名直接发 Return——quotation 151→140
（11 个函数退化）。原因：该签名亦出现于多语句块/其他语义位置，GBS 层过早
认领会破坏既有正确路径。正确切入点应是**块分发层**（_process_if_blocks 的
角色判定/then-arm 组装），并需先解释「为何同签名在 quotation 中被现有路径
正确处理而在本家族中不被」——差异在块的**前驱拓扑**而非指令序列本身。
