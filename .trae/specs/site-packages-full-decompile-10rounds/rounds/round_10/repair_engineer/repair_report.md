## 二、根因与改动

### 改动 1（主因）：region_ast_generator.py `_generate_with`

pre-BEFORE_WITH 前缀提取只回溯到「最近一条 STORE_*」，把前缀截断为最后一条
赋值；落在 STORE_* 与 BEFORE_WITH 之间的 CALL…POP_TOP 兄弟表达式语句既不在
前缀发射范围、也不在 ctx 提取范围（items 从终结符之后开始），被整体丢弃。
幸存指纹吻合：STORE_* 结尾的赋值/augassign 幸存，POP_TOP 结尾的表达式语句丢失。

修复：回溯终止条件扩为**语句终结符集合**
`{STORE_FAST, STORE_NAME, STORE_GLOBAL, STORE_DEREF, STORE_SUBSCR, STORE_ATTR, POP_TOP}`；
终结符及其之前的完整语句单元经 `_build_statements_from_instructions`
（按 STORE/POP_TOP/RETURN 边界切分，含 import/unpack 状态机）全部发射为顺序
前置语句。裸 STORE（循环目标）无值表达式时 `_build_store_statement` 返回 None，
不会与循环目标双发。同步更新 `_generate_with` docstring「字节码一致性约束」节。

### 改动 2（触发面 B 的块归属根因）：region_analyzer.py `_find_try_else_blocks`（Pattern TE 分支）

R51「JUMP_FORWARD 目标是否 handler 可达」BFS 沿后继扩展时穿过了 continue 的
JUMP_BACKWARD 回边 → 循环头 → 整个循环体（含 try 体自身及其 JUMP_FORWARD 出口），
把 post-try 顺序代码误判为 handler 可达，从而将 try/except 之后的兄弟块
（use(v)+with 等）收编为 else_blocks，渲染成 try/except/else —— 字节码布局从
[JUMP_FORWARD 跳过内联 handler][handler][后续] 变为 [fall-through 直落后续][handler 尾置]，
co_code 差 2 字节（repro_06/07 修复后残留差异即此）。

修复：handler 块以 JUMP_BACKWARD（continue/back-edge）终止时不沿后继扩展——
依 R51 本义「handler 以 return/break/continue/reraise 终止」+ 控制流边判据：
真正的 handler→目标前向可达性不经由向后跳转边。

### 最终边界判定规则（with 入口前置段）

1. 从 BEFORE_WITH 向前回溯，遇终结符（六种 STORE_* 或 POP_TOP）停止：
   终结符及之前 = 完整语句单元，归属函数体顺序序列并发射；
   终结符之后到 BEFORE_WITH = with 上下文表达式，归属 region.items。
   与 `_extract_with_items` 的 ctx 边界互补，无重叠、无遗漏、无 depth 硬编码、
   无 pyc 特判、无反模式前缀命名。
2. try/except 后兄弟位归属：try 体正常出口以 JUMP_FORWARD 越过完整内联
   handler 区间到达目标，且所有 handler 均终止（return/break/continue/reraise，
   BFS 不穿越向后跳转边验证）→ 目标是 post-try 顺序代码而非 else 子句。
