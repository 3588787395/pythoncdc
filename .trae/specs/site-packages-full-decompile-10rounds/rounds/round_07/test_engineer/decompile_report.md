## 二、根因 A：docstring 被丢弃（常量表错位）

### 现象

原函数 `check_strategy.co_consts[0]` 为文档字符串：

```text
'\n    检查用户策略在升级过程中是否涉及量化方法和库变动。\n    :param strategy_content: 策略内容(str)\n    :param strategy_path: 策略路径(str)...'
```

但反编译输出的函数体不含该 docstring。反编译文本 re-compile 后，CPython 3.11 编译器按"无 docstring"处理，导致常量表索引整体偏移 1：

- 有 docstring 时：`const[0] = docstring`，`None` 懒插入到后续位置；
- 无 docstring 时：`None` 占据 `const[0]`。

于是所有引用常量的指令参数错位 1（`LOAD_CONST` / `KW_NAMES` 的 arg 全部偏移），co_code 无法字节级相等。

### 最小复现

```python
import sys; sys.path.insert(0, r'F:\Downloads\pythoncdc-main')
from core.cfg import decompile
print(decompile("def f(x):\n    'doc here'\n    return x + 1\n"))
# 输出：
# def f(x):
#     return x + 1        ← 'doc here' 丢失
```

实验已验证输出丢失 `'doc here'`。

## 三、根因 B：嵌套 if 被扁平化为 and 链

### 原源码形态

```python
if strategy_content is not None:
    if strategy_path is not None:
        strategy_log.warning(...)      # then 块
else:
    strategy_content = open(...)       # else 块
```

### 字节码证据（原 pyc，offset 为绝对偏移）

```text
552 POP_JUMP_FORWARD_IF_NONE      to 600   ← 外层条件为假 → 跳到 else 块入口(600, LOAD_GLOBAL open)
554 LOAD_FAST                     strategy_path
556 POP_JUMP_FORWARD_IF_NONE      to 598   ← 内层条件为假 → 跳到 then 块末尾 JUMP_FORWARD(598)
596 POP_TOP
598 JUMP_FORWARD                  to 672   ← then 块结束跳转
600 LOAD_GLOBAL                   NULL + open   ← else 块入口
```

关键特征：**两个条件的 false 跳转目标不同**——外层目标是 else 块入口 `600`，内层目标是 then 块末尾的 `JUMP_FORWARD`(598)。

### 缺陷行为

反编译器把两个条件折叠成单个 `if A and B:` 输出，只生成一个 `POP_JUMP_FORWARD_IF_NONE`，其 false 目标只能指向一个地址，导致与原 pyc 相比差一个字节码单元（600 vs 598），指令序列与条数均不同（289 vs 290）。

### 判定规则（修复依据）

只有当各子条件的 false 跳转目标指向**同一块**时才是真正的 and 链，才能合并；否则必须保持嵌套 if 结构。
